## Model and resource evidence

Qwen3.8-27B Q3_K_M model SHA-256 `7f3b845b563888ec3abc269474cf744bf703a7ce8766dbb7f696c63975facfd7`; llama.cpp binary SHA-256 `3f1000482d759661cadb1dc9b59f6292f52408ee0d2906298fa001837517fb4e`. CPU-only, context 32768, one server slot, temperature zero, thinking disabled, STANDARD context profile, at most ten model turns with 768 output tokens per request. A fresh owned server per task was stopped after execution. Existing model installations were not changed.

Provider-reported totals: 24 model calls; 18,284 fresh input, 48,400 cached input, 2,391 output, 69,075 total tokens; 2,494.044 summed Job wall seconds. Per verified success: 17,268.75 total tokens and 623.511 summed wall seconds. Canonical invocation adapter accounting remains UNATTESTED; these totals come from retained actual HTTP usage fields. Cost: NOT APPLICABLE — LOCAL INFERENCE. Energy: NOT MEASURED.

Containment used networkless read-only worker containers, dropped capabilities, no-new-privileges, bounded resources and scratch space. Only the frozen fixture, qualification driver, output directory and restricted model proxy socket were mounted. Scope/escape checks are retained per task. A separate host-network proxy admitted only the owned local model paths. No credentials, user home, production state or unrelated data was mounted into model workers.

This used ordinary JobRuntime/JobCatalog, generic registered actions, authority leases, permission/tool policy, scoped mutation, artifacts and independent verification. No benchmark action adapter was registered. The custom qualification JobRuntime did not configure the complete service RuntimeSafetySupervisor. This is stronger integration evidence than a standalone parser, but does not establish a deployed, ordinary configurable semantic Job path. Frozen fixture/verifier helpers were reused; no generalisation claim follows from the five tasks.

## Faults, diagnostics and limitations

Final delivery workload ran 18 physical Jobs against an explicitly controlled HTTP source, without model inference. A progressing control succeeded while another Job was cancelled or terminated for repeated reads. Warning, recovery-required, replanning, escalation-required and governed termination records were observed. The recovery source was scripted to change its response; this is not proof of autonomous model recovery. No paid escalation occurred.

The delivery diagnostic reconciliation paired 56 dispatch starts with terminal outcomes: 56 correct, 0 incorrect, 0 unknown under that narrow mechanical check. This is not a general failure-classification evaluation or independent human review. It is separate from the earlier 264-event research reconciliation and the v4.13 AI-reviewed 47-case evaluation. The genuine model driver retained recipe IDs in semantic event runId fields; the receipt supplies the recipe-to-Job mapping and does not overwrite raw records. Global Job attribution is therefore not claimed clean without reconciliation.

Earlier module-loader/transport setup failures and all fault assessor mismatches remain retained. The last model task's public tests rejected an extra cacheWriteTokens field; no false success was published. No-progress did not mistake its slow active generation for a repeated-read loop.

Single disposable VM startup samples were 19.649s (baseline), 17.679s (candidate), 17.949s (rollback); post-Job RSS samples were 187552, 170308 and 174896 KiB. These are not idle measurements or controlled statistical performance evidence. Per-tool/event/tracker overhead and long-duration resource stability remain unqualified. Mixed faults and the 41.6-minute summed model workload are bounded qualification, not endurance evidence.
