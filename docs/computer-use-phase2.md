# Computer Use Phase 2 experimental desktop candidate

The generic `ComputerUseCapability` remains provider neutral. The Windows candidate implements its provider contract through an exact-window, loopback-only Sky bridge. A separate embedded qualification adapter uses the same contract while the desktop runtime is active. Both record interaction mode, coordinate fallback, screenshots, and fresh observations.

This is **EXPERIMENTAL**. The desktop Job manifest is disabled. A standalone Agent Control process cannot currently drive Sky through a background bridge callback: the desktop execution context is absent outside an active desktop tool invocation. The bridge tests use a fake Sky implementation, and the physical Blender run used the embedded adapter. Do not enable production routing on the basis of this candidate.

The MSI qualification used a newly launched Blender 4.5.10 LTS window. It changed the default cube to scale `(2, 2, 2)` and location `(1, 0, 0)`, saved an isolated `.blend`, and independently reopened that file with Blender in batch mode. A separate batch export produced a small GLB. The GLB export did not go through the desktop Computer Use provider.

The qualification also found a dialog-targeting defect: Sky returned both a parent screenshot and a child dialog screenshot. The first adapter revision used the parent image while targeting the dialog. The candidate now selects the last, window-specific image and rejects changed dimensions. The original failed action and its recovery remain in the private qualification evidence. A save confirmation closed its dialog before the next observation, so that action reported `FAILED` even though independent verification found the saved file. This transition needs a generic parent-window handoff before the whole Job may return `COMPLETE`.

Security boundaries: bind the exact window ID and application, reject protected titles, reject stale revisions and changed screenshot dimensions, allowlist keys, require explicit policy for coordinate actions and screenshots, and keep screenshots and token material outside Git. No UAC or security dialog automation is supported. Accessibility inspection of Blender exposed only window chrome; the physical scene operations used keyboard input and recorded coordinate fallback. Video remains `BLOCKED` when requested. Approval pause exists, but trusted persisted resume is not yet implemented. Dashboard summary fields are present; a physical dashboard rendering of this run has not been qualified.

Promotion requires a standalone desktop runtime with reliable window focus and modal handoff, trusted persisted approval/resume, observed file verification in the governed Job, physical dashboard rendering, and a clean full regression on the target platform.
