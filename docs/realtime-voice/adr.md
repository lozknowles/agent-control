# ADR: WhatsApp realtime voice transport

Date: 2026-09-05. Decision: **prefer the official Calling API media boundary for an eventual supported adapter; enable no WhatsApp calling transport in this candidate**. The existing OpenWA voice-note path remains supported as the private pilot. The reusable session layer is EXPERIMENTAL/PARTIAL, not a full-duplex product.

## Evidence examined

The installed OpenWA gateway is the rmyndharis/OpenWA project, not the similarly named open-wa/wa-automate package. Its v0.23.4 call service and engine interface expose rejectCall and createCallLink. No accept/media API was found. Its documented [calls API](https://docs.open-wa.org/api-reference/calls/) agrees. [whatsapp-web.js Call](https://docs.wwebjs.dev/Call.html) exposes metadata and rejection, not bidirectional media. Browser call capability flags alone do not provide a supported PCM hook.

[MeowCaller](https://github.com/purpshell/meowcaller), inspected at `27a3c6b18657614c9ec2ed16dfc497eff11de6ec`, is a plausible independent call client: Receive attaches a 16kHz mono PCM sink; Play/Player.Stop supplies and stops output. CallRegistry.AbortAll must be wired by the integrator on disconnect. Its [disclaimer](https://github.com/purpshell/meowcaller/blob/27a3c6b18657614c9ec2ed16dfc497eff11de6ec/DISCLAIMER.md) describes an unofficial interoperability research protocol, not an endorsed service. MIT code; whatsmeow and transitive licensing still need an adapter-level dependency inventory. The README lists incomplete Opus fallback. No account session was imported or paired during this inspection.

[whatsapp-rust](https://github.com/oxidezap/whatsapp-rust) independently advertises 1:1 MLOW/encoded Opus media and modular transports under MIT. It explicitly warns about unofficial-client account suspension risk. It is another credible experimental candidate, not evidence that this account/device combination works.

The [official Calling API documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/calling) returned HTTP 429 through the documentation fetch. Current eligibility, coexistence and account-specific availability therefore remain unverified. The [WebRTCventures reference implementation](https://github.com/WebRTCventures/whatsapp-webrtc-application) demonstrates webhook SDP signaling to a WebRTC peer and identifies a Business API account, token and publicly reachable webhook as prerequisites. Its source is useful architectural evidence, not a production security implementation to copy. No verified Calling API configuration exists in this pilot; no migration, public webhook or new account was created.

## Consequences

Do not replace/re-pair the working gateway or infer call authority from phone/display names. Add a separately authenticated and operator-approved exact caller binding before enabling any adapter. MeowCaller remains a technically credible experimental alternative for a separately scoped account/device qualification; it is not dismissed as incapable, nor represented as safe/reliable on an untested account.

The present blocker is **no qualified authenticated WhatsApp call-media transport or Calling API setup**. The implementation provides the session/audio/security boundaries that can be reused when that prerequisite exists. It intentionally contains no fake call-accept API, browser-audio success animation or claim that streamed voice-note chunks equal full duplex.
